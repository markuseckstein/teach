Lesson 1: The SDD Loop

≈10 minutes · Mission: ship features on your Spring Boot + Angular project spec-first

The one idea

You already know what happens in Copilot agent mode on a non-trivial feature: the first prompt goes well, the third one contradicts the first, and by the end the real requirements exist only in your chat scrollback. Next week, neither you nor the agent can reconstruct why the code looks the way it does.

Spec-Driven Development flips the primary artifact. Instead of prompts producing code directly, prompts produce a specification — a Markdown file in your repo — and the code is derived from it. When requirements change, you change the spec and re-derive, rather than archaeologically prompting at the code. GitHub's announcement post puts it as: the spec becomes the source of truth, and code becomes its expression (GitHub Blog).

Anchor to what you know You already work this way at the API layer: your OpenAPI spec is the contract, and the Spring controllers and Angular clients are generated expressions of it. Nobody on your team hand-edits a generated client and calls it done — they fix the contract. SDD applies that same discipline one level up, to the feature itself.

The artifact chain

Spec Kit operationalizes SDD as a pipeline of Markdown artifacts, each produced by a slash command you run in Copilot (Quick Start):

/speckit.constitution   →  constitution.md   the project's non-negotiable principles (once per project)
/speckit.specify        →  spec.md           WHAT the feature does and WHY — no tech allowed
/speckit.clarify        →  spec.md (refined) the agent interviews YOU about ambiguities
/speckit.plan           →  plan.md           HOW: stack, architecture — your OpenAPI contract is born here
/speckit.tasks          →  tasks.md          ordered, dependency-aware implementation steps
/speckit.analyze        →  (report)          consistency check across spec ↔ plan ↔ tasks
/speckit.implement      →  code              the agent executes tasks.md

Two properties make this more than bureaucracy:

  • Each phase is a cheap checkpoint before an expensive one. Fixing a wrong assumption in spec.md costs a sentence; fixing it after /speckit.implement costs a refactor. clarify and analyze exist purely to catch problems while they're still cheap.
  • The what/how separation is enforced by phase. "Spring Boot" appearing in spec.md is a smell — technology belongs in plan.md. This matters doubly for you: one feature spec can drive a plan that spans both your backend and frontend, because the spec itself is stack-neutral.

Full command table, including the optional checklist and converge commands, is in the workflow cheat sheet.

One terminology trap

Your project has two things called a "spec": the SDD feature spec (Markdown, what/why) and the OpenAPI spec (YAML/JSON, API contract). They live at different levels: the feature spec drives the plan, and the plan produces or updates the OpenAPI contract as one of its outputs. When Spec Kit docs say "spec", they always mean the feature spec. The glossary pins this down — it's the vocabulary this course will hold to.
