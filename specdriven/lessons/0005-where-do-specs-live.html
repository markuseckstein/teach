Lesson 5: Where Do the Specs Live?

≈20 minutes, concept + hands-on layout · your session-1 question, now with the evidence · builds on Lesson 4

The question

You have backend (Spring Boot) and frontend (Angular), separate repos, one OpenAPI contract between them. A feature spec describes behavior that spans both. So where does Spec Kit get initialized — backend repo, frontend repo, or somewhere else?

The decision rule

From the maintainers, in the discussion that asked exactly your question (spec-kit #1743):

The constitution heuristic Would backend and frontend share one constitution? Same product, same team, same quality rules, features spanning both → one project: specs live above both repos. Different constitutions (different teams, release cadences, standards) → genuinely separate projects, each with its own specs.

Your case answers itself: every feature flows through the shared OpenAPI contract, so the two repos are one product wearing two runtimes. One constitution, one spec tree — above both repos.

Why not backend? Why not frontend?

Lesson 4 gave you the structural reason. A spec is deliberately technology-free — it describes behavior, not Spring or Angular. Putting it inside one implementation repo:

  • Breaks the symmetry. The spec would be versioned, branched, and PR-reviewed under one repo's lifecycle while governing both. The other repo becomes a second-class citizen that can't even see the requirements it implements.
  • Blinds the agent. When Copilot plans or implements from a spec in backend/, the Angular code doesn't exist as far as it's concerned. Cross-repo features need the agent to see both codebases.
  • Inverts the ownership. The spec sits above even the OpenAPI contract (spec → plan → contracts/). Storing it in the backend implies the backend owns the product's requirements. It doesn't — it implements half of them.

The two workable layouts

Umbrella workspace (recommended start)A local folder with both repos cloned inside and Spec Kit initialized at the top, outside either repo's git.Agent sees both codebases when planning and implementing; zero new infrastructure; one specs/ tree.The workspace top isn't itself a repo (unless you make it one) — sharing specs with the team needs layout B or committing the umbrella.

These compose: start with A, graduate to B by turning the umbrella's specs/ + .specify/ into the third repo once the team needs shared access. B-without-A (specs repo alone) is the weakest option — the agent can read requirements but not the code they govern.

The umbrella, concretely

product-workspace/            ← specify init here, --no-git
├── .github/prompts/          ← /speckit.* commands available when VS Code opens THIS folder
├── .specify/                 ← templates, scripts, constitution memory, feature.json
├── specs/
│   └── 001-bookmark-customers/
│       ├── spec.md  plan.md  tasks.md
│       └── contracts/openapi.yaml   ← the hand-off point between the two repos
├── backend/                  ← git repo #1 (Spring Boot)
└── frontend/                 ← git repo #2 (Angular)

The catch that used to bite — and its fix

Spec Kit historically used the git branch name as its feature state (001-bookmark-customers), which is why monorepo and multi-repo users struggled (#769, #1095). That's fixed in current Spec Kit: git support moved to an optional extension, and with --no-git the feature state lives in .specify/feature.json (or the SPECIFY_FEATURE env var) — verified directly in the helper scripts. Consequence: the umbrella needs no git of its own, and Spec Kit won't fight the two inner repos' branch management. Feature branches in backend/frontend remain entirely yours to manage.

This area is still evolving — the maintainer acknowledged multi-repo support as a known gap being worked on (#1743). Re-check the discussions before you cement team conventions.

Do it — build the umbrella

  1. Create the workspace and clone (or for practice, git init two stub folders): 
    mkdir -p ~/work/product-workspace && cd ~/work/product-workspace
git clone <backend-url> backend
git clone <frontend-url> frontend
  2. Initialize Spec Kit at the top, gitless: 
    uvx --from git+https://github.com/github/spec-kit.git \
  specify init . --ai copilot --script sh --no-git
  3. Verify: ls .github/prompts .specify at the workspace root; backend/.git and frontend/.git untouched; no .git at the top.
  4. Open the workspace folder in VS Code (code ~/work/product-workspace) — not a single repo. Type /speckit. in Copilot Chat: the commands are there, and the agent's file context now spans both repos.
  5. Port your Lesson 3 constitution into .specify/memory/constitution.md — it was written for exactly this two-repo product.

Check yourself

1. What single question decides whether two repos share one spec tree?
2. With --no-git, how does Spec Kit know which feature is active?
3. Why is a dedicated specs repo alone weaker than specs-repo-inside-umbrella?
