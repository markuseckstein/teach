Lesson 4: Specify → Clarify → Plan

≈35 minutes, hands-on in ~/sdd-playground · builds on Lesson 3 — your constitution must exist first

The win you're after

One practice feature taken from an English sentence to a reviewed spec.md, a clarified set of requirements, and a plan.md whose contracts/ directory holds a generated OpenAPI contract. That last artifact is the payoff for your stack: the plan phase is where your two repos' shared contract is born.

The one idea: ambiguity is load-bearing

The spec template treats unknowns as first-class: requirements the agent can't pin down get marked [NEEDS CLARIFICATION: …] instead of silently guessed (spec-template.md). /speckit.clarify then turns those markers into an interview — the agent asks you. This inverts your agent-mode habit: instead of you prompting harder, the workflow extracts the requirements you didn't know you hadn't stated. A first-pass spec with zero markers isn't impressive, it's suspicious — it means the agent guessed.

Do it

Step 1 — Specify (what/why only)

The practice feature is deliberately API-shaped, like your day job. In Copilot Chat, agent mode:

/speckit.specify Team members can bookmark customer records and see their
bookmarks in a list. A bookmark can carry an optional short note. Bookmarks
are private to the team member who created them. The list shows the most
recently bookmarked customers first and lets the user jump to the customer
or remove the bookmark.

Note what the prompt does not say: no endpoints, no tables, no Angular components. Spec Kit creates a branch like 001-bookmark-customers and specs/001-…/spec.md.

Verify against the checklist: prioritized user stories (P1 must stand alone as an MVP), Given/When/Then acceptance scenarios, numbered FR-NNN requirements, measurable success criteria — and grep the file for stack words: grep -inE 'spring|angular|rest|http|sql' specs/001-*/spec.md should come back empty.

Step 2 — Clarify (answer like a product owner)

/speckit.clarify

Expect questions like: maximum note length? What happens when the bookmarked customer is deleted? Is there a bookmark limit? Answer decisively — invented-but-consistent answers beat "whatever you think." This is deliberate practice for the skill that matters at work: you'll be the one answering these for real features.

Verify: the [NEEDS CLARIFICATION] markers are gone from spec.md and your answers appear as a Clarifications section / sharpened requirements. Any marker still standing → run clarify again.

Step 3 — Plan (now, and only now, the tech)

/speckit.plan The backend is Spring Boot 3 (Java 21, Maven), the frontend
Angular with the OpenAPI Generator toolchain. Backend and frontend live in
separate repositories and communicate exclusively through a versioned
OpenAPI 3.1 contract; server stubs and the Angular client are generated
from it. Persistence: PostgreSQL via Spring Data JPA.

Verify — three gates, in order:

  1. Constitution Check passed? Open plan.md — the gate section must exist and pass. If the plan proposes hand-written API DTOs, your Lesson 3 constitution should have flagged it. If it didn't, your constitution has a hole: go sharpen Article I and re-plan. That loop — plan violates, constitution catches, you tighten — is SDD working as designed.
  2. Contract born? ls specs/001-*/contracts/ — expect an OpenAPI YAML. Audit it like a PR from a colleague: every user story reachable through some endpoint, bookmarks filtered to the current user, the note's max length from your clarify answer encoded as a schema constraint.
  3. Entities faithful? data-model.md entities match the spec's Key Entities — same names, nothing invented.
Why this matters for your two repos Everything above contracts/ is repo-neutral — which is exactly why the specs shouldn't live in the backend or frontend repo (the Lesson 1 discussion). The contract is the hand-off point: one spec, one plan, one OpenAPI file — then two repos generate their halves from it.

Check yourself

1. A first-pass spec has zero [NEEDS CLARIFICATION] markers. Why is that a warning sign?
2. Which phase produces the OpenAPI contract file?
3. What must be true of the P1 user story on its own?
