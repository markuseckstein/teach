Artifact Quality Checklist

Reference · what "good" looks like for each Spec Kit artifact — use when reviewing what the agent generated

constitution.md

  • Every article is enforceable. Test: could a reviewer objectively say "this PR violates article III"? "Code should be clean" fails the test; "generated API code is never hand-edited" passes.
  • Non-negotiables are explicitly marked (NON-NEGOTIABLE).
  • It contains principles, not feature ideas or a tech wishlist. Stack choices belong here only when they are law ("all services are Spring Boot"), not preference.
  • Has a Governance section + version and ratification date (the template footer: Version | Ratified | Last Amended).
  • Short. If an article never changes a decision, delete it.

spec.md

  • Zero technology. Grep it for your stack words (Spring, Angular, REST, JPA, HTTP) — every hit is a leak from the plan phase.
  • User stories are prioritized (P1, P2, P3…) and independently testable — implementing only P1 must still yield a viable slice.
  • Acceptance scenarios are Given/When/Then, concrete enough to become tests.
  • Functional requirements are numbered (FR-001…) and each says MUST + one specific capability.
  • Unknowns are marked [NEEDS CLARIFICATION: …], not silently guessed. A spec with zero markers on the first pass is suspicious, not impressive.
  • Success criteria are measurable and technology-agnostic ("account creation under 2 minutes", not "fast API").

plan.md (and friends)

  • Constitution Check section exists and passes — it's the gate before research and after design. A plan that skipped the gate is invalid.
  • Technical Context has no lingering NEEDS CLARIFICATION — that's unresolved risk headed for the tasks phase.
  • Project structure reflects reality (for you: backend/ + frontend/ web-app layout, or your two-repo workspace).
  • contracts/ contains the API contract — for your stack, the OpenAPI YAML. Check: every user story in the spec is reachable through some endpoint in the contract; every endpoint traces back to a requirement.
  • data-model.md entities match the spec's Key Entities — same names, no inventions.

Cross-artifact (what /speckit.analyze checks)

  • Every FR-NNN maps to at least one task; every task maps back to a requirement or the plan.
  • No contradiction between constitution and plan (e.g. constitution says contract-first, plan hand-writes controllers).
  • Terminology is consistent — the same entity isn't "Customer" in the spec and "Client" in the data model.
