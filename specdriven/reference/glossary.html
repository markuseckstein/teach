SDD Glossary

Reference · the course's fixed vocabulary — lessons adhere to these meanings

TermMeaning in this course
Spec-Driven Development (SDD)Methodology where a written specification is the primary artifact; code is derived from it by an AI agent. Contrast: "vibe coding" (prompt → code, no durable artifact).
Spec KitGitHub's open-source toolkit for SDD: templates, helper scripts, and slash commands installed into a repo. Agent-agnostic (30+ integrations).
specify CLIThe Python bootstrap tool (run via uvx/pipx) that installs Spec Kit scaffolding into a project. You run it once per project — it is not the thing that writes specs.
/speckit.specifyThe slash command (inside Copilot) that creates a feature spec. Easily confused with the CLI above; they are different tools.
Feature spec (spec.md)Markdown document describing what a feature does and why — user journeys, requirements, acceptance criteria. Deliberately technology-free.
OpenAPI specMachine-readable REST API contract (YAML/JSON). ⚠ Both are called "spec" — in SDD conversation, "spec" means the feature spec. The OpenAPI spec is a contract artifact produced during the plan phase.
Constitutionconstitution.md: the project's immutable principles (stack, testing policy, conventions). Checked by every phase; the highest-authority artifact.
Plan (plan.md)The how: architecture and tech decisions that satisfy the spec under the constitution. Where Spring Boot, Angular, and OpenAPI Generator get named.
Tasks (tasks.md)Ordered, dependency-aware breakdown of the plan into implementable steps.
AgentThe AI doing the work — for this course, GitHub Copilot (VS Code agent mode or Copilot CLI).
Copilot CLIGitHub's terminal-based Copilot agent (copilot command). Distinct from both the gh CLI and the specify CLI.
Vibe codingConversational prompt-to-code with no durable specification. The failure mode SDD exists to fix: intent lives in chat scrollback, not in the repo.
