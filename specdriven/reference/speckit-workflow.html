The Spec Kit Workflow

Reference · cheat sheet for the command loop and its artifacts

The loop at a glance

constitution ──▶ specify ──▶ clarify ──▶ plan ──▶ checklist ──▶ tasks ──▶ analyze ──▶ implement
 (principles)    (what/why)  (de-risk)  (how)     (quality)     (steps)   (consistency)  (code)

Each phase writes a Markdown artifact into specs/<NNN-feature-name>/. The artifact — not your chat history — is the context the agent works from.

Commands

CommandProducesPurpose / when to run
/speckit.constitutionconstitution.mdOnce per project. Non-negotiable principles: stack, testing rules, conventions. Every later phase must comply with it.
/speckit.specifyspec.md + feature branchStart of every feature. Describe what and why — no tech choices here.
/speckit.clarifyupdates spec.mdAgent interviews you about ambiguities. Run before planning; skipping it is the #1 source of rework.
/speckit.planplan.md (+ research, data model, contracts)Now the tech enters: stack, architecture, API contracts (your OpenAPI spec belongs here).
/speckit.checklistchecklist filesOptional quality gates: custom validation lists for the spec/plan.
/speckit.taskstasks.mdBreaks the plan into ordered, dependency-aware tasks.
/speckit.analyzereport (read-only)Cross-checks spec ↔ plan ↔ tasks for gaps and contradictions. Last stop before code.
/speckit.implementcodeAgent executes tasks.md. For big features, implement phase-by-phase to protect context.
/speckit.convergereportPost-implementation: verifies completion, lists remaining work.

Bootstrap (Git Bash)

# one-off run, nothing installed permanently
uvx --from git+https://github.com/github/spec-kit.git specify init <PROJECT> --ai copilot --script sh

# or in an existing repo
uvx --from git+https://github.com/github/spec-kit.git specify init . --ai copilot --script sh

--script sh forces the POSIX-shell helper scripts — the right choice for Git Bash on Windows, where auto-detection may pick PowerShell. --no-git skips branch management if you need to own that yourself.

Rules of thumb

  • Spec = what/why. Plan = how. Tech stack mentioned in a spec is a smell.
  • Commands detect the active feature from the branch name (001-feature-name).
  • Artifacts are Markdown in your repo — review them in PRs like code.
  • Don't skip clarify or analyze: they are the cheap checkpoints; implement is the expensive one.
