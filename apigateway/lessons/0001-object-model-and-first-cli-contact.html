Lesson 0001 · IBM API Connect v10 · ~15 minutes

The Object Model & First CLI Contact

Learn the seven nouns that explain everything, then prove — from your terminal, against your real environment — that you never need the UI.

First, your burning question

Yes, there is a full automation surface. Everything the API Manager UI does goes through the Platform REST API, and IBM ships a CLI, the apic toolkit, that wraps it. You can publish an openapi.yml, download every spec in a catalog, and script all of it. The UI is optional. Today you make first contact; publishing is Lesson 2.

The seven nouns

API Connect looks over-engineered until you see that it models two audiences: providers (you, publishing APIs) and consumers (app developers calling them). Seven objects connect the two:

Provider organization (pOrg) ← your team's home; you develop here ├── Draft APIs & Draft Products ← your openapi.yml lives here, runs nowhere └── Catalog (Sandbox, dev, prod…) ← a runtime environment on a real gateway ├── Product ← the unit of publishing: bundles APIs + Plans │ ├── Plan ← rate limits + subscription terms ◄──┐ │ └── API ← your openapi.yml, now live │ └── Consumer organization │ └── Application (client id/secret) ── subscribes to a Plan ─────┘

The one rule that explains everything

You never publish an API directly. You publish a Product into a Catalog. Consumers' apps subscribe to a Plan inside that Product. Every command, REST path, and UI screen is downstream of this rule.

In practice: a Catalog behaves like an environment (it's bound to a gateway cluster and optionally a Developer Portal), a Product behaves like a versioned release artifact with a lifecycle (staged → published → deprecated → retired), and your openapi.yml — with IBM's x-ibm-configuration extension carrying the "custom pipeline" (the assembly, Lesson 4's topic) — rides along inside it. The full noun-by-noun breakdown, including Spaces and Subscriptions, is in the object-model reference — bookmark it.

Hands-on: first contact, read-only

Everything below is safe: list operations only. You need the toolkit binary and your management endpoint (the hostname behind your API Manager UI; ask your platform team for the "platform API endpoint" if unsure).

# 0. Get the toolkit (one-time): IBM Fix Central, or — one last UI sin —
#    API Manager → help (?) menu → "Download toolkit". A single binary.

# 1. What version is my work environment? (report this back to your teacher)
apic version

# 2. Which realm do I log in against?
apic identity-providers:list --scope provider --server $MGMT

# 3. Log in (use the realm name from step 2, often provider/default-idp-2)
apic login --server $MGMT --realm provider/default-idp-2 --username you@company.example

# 4. Which provider orgs am I a member of?
apic orgs:list --server $MGMT

# 5. The win: which catalogs can I publish to?
apic catalogs:list --server $MGMT --org $ORG

The --debug trick

Re-run step 5 with --debug appended. The toolkit prints the raw HTTPS requests it makes — method, URL, headers. This is the Platform REST API, live from your own installation. Anything apic can do, your CI pipeline can do with curl. Keep this trick; it's how you'll discover endpoints in Lesson 5.
