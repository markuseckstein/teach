Lesson 0002 · IBM API Connect 10.0.11 · ~20 minutes

Publish Your First API

Two YAML files and one command. No UI was harmed in the making of this lesson.

You know from Lesson 1 that the unit of publishing is the Product. So publishing takes exactly two files: your OpenAPI definition, and a small product YAML that wraps it. Both examples below are taken (lightly trimmed) from IBM's own example-toolkit-scripts repo and target your gateway type, the native DataPower API Gateway.

File 1: the API — your OpenAPI plus x-ibm-configuration

Save as findbranch_1.0.0.yaml. It's a plain Swagger 2.0 document; everything API Connect adds lives under two IBM extensions:

swagger: "2.0"
info:
  title: FindBranch
  x-ibm-name: findbranch          # ← the machine name; lowercase, stable
  version: 1.0.0
schemes: [https]
basePath: /findbranch             # ← path on the gateway
security:
  - clientID: []
securityDefinitions:
  clientID:                       # apps authenticate with their client ID
    type: apiKey
    in: header
    name: X-IBM-Client-Id
paths:
  /details:
    get:
      responses:
        "200":
          description: 200 OK

x-ibm-configuration:              # ← everything the gateway needs
  gateway: datapower-api-gateway  # ← your gateway type (native, not v5c)
  enforced: true                  # gateway enforces security & limits
  testable: true
  phase: realized
  cors:
    enabled: true
  properties:                     # ← name/value config, referenced as $(name)
    target-url:
      value: https://backend.example.com/branches
      description: The URL of the target service
  assembly:                       # ← the "custom pipeline" (Lesson 4!)
    execute:
      - invoke:                   # simplest pipeline: one proxy step
          title: invoke
          version: 2.0.0
          verb: keep
          target-url: $(target-url)

Note the shape

Your existing openapi.yml stays intact — API Connect only adds the x-ibm-name and the x-ibm-configuration block. The assembly.execute array is the pipeline you asked about: an ordered list of policies the gateway runs on every request. Here it's a single invoke (proxy to backend); Lesson 4 adds real logic.

File 2: the Product — plans, visibility, and which APIs ride along

Save as findbranch_prod_1.0.0.yaml:

product: 1.0.0                    # product schema version, not your version
info:
  name: findbranch-product
  title: Find Branches
  version: 1.0.0
gateways:
  - datapower-api-gateway
apis:
  FindBranch:
    $ref: findbranch_1.0.0.yaml   # ← local file; uploaded with the product
visibility:
  view:      { enabled: true, type: public }
  subscribe: { enabled: true, type: authenticated }
plans:
  default:
    title: Default Plan
    approval: false               # true = subscriptions need approval
    rate-limits:
      default:
        value: 100/hour           # the Plan is where limits live
        hard-limit: false

Validate, publish, verify

# 1. Lint both files before they leave your machine
apic validate findbranch_prod_1.0.0.yaml

# 2. Publish product + API into a catalog, in one shot
apic products:publish findbranch_prod_1.0.0.yaml \
     --server $MGMT --org $ORG --catalog sandbox

# 3. Verify: what's in the catalog now?
apic products:list-all --server $MGMT --org $ORG \
     --scope catalog --catalog sandbox

That's it. The product is published: live on every gateway the catalog is bound to, at https://<gateway-api-endpoint>/<org>/<catalog>/findbranch/details. Calling it still requires a subscribed application's X-IBM-Client-Id — consumer-side mechanics come later.

Variant: stage now, go live later

apic products:publish --stage findbranch_prod_1.0.0.yaml \
     --server $MGMT --org $ORG --catalog sandbox

--stage parks the product in the catalog in state staged — present, reviewable, but not serving traffic. The lifecycle you saw in the reference (staged → published → deprecated → retired) is driven by products:replace / products:supersede — that's the CI/CD lesson.

Check yourself

Primary source

Skim IBM's doapic-prod.bash (5 minutes) — an official, working script that publishes, stages, replaces, and deletes products. It is the distilled version of everything in this lesson plus a preview of the lifecycle commands. The prose reference is IBM Docs: Creating and validating API and Product definitions by using the CLI.

Homework: publish FindBranch (or a trimmed copy of one of your real openapi.yml files with the x-ibm-configuration block bolted on) to your work Sandbox catalog, then delete it again with apic products:delete --server $MGMT --org $ORG --scope catalog --catalog sandbox findbranch-product:1.0.0. First confirm with your team that the Sandbox catalog is fair game. Anything odd — validation errors, missing permissions — bring it to your teacher.
