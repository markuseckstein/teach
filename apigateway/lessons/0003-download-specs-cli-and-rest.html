Download Specs — CLI & Raw REST

Everything that's in a catalog can come back out: whole-catalog exports with one command, single specs on demand, and — for your CI pipeline — the same thing with nothing but curl.

Part A: the CLI read path

Publishing (Lesson 2) has a mirror image. Three commands cover it:

# The big one: download EVERY product + API in a catalog as YAML files
# (your instant catalog backup / "what is actually deployed?" answer)
apic products:clone --server $MGMT --org $ORG \
     --scope catalog --catalog sandbox

# One product's definition (plans, visibility, referenced APIs)
apic products:get findbranch-product:1.0.0 --server $MGMT --org $ORG \
     --scope catalog --catalog sandbox

# One API's OpenAPI document, as deployed
apic apis:get findbranch:1.0.0 --server $MGMT --org $ORG \
     --scope catalog --catalog sandbox

Each get writes a YAML file into your current directory; add --output - to dump to stdout instead (pipe it into yq/jq), and --format json if you prefer JSON. The same verbs exist for development artifacts in the pOrg: draft-apis:get, draft-products:get, draft-apis:list-all.

Catalog vs. drafts — which do you want?

apis:get --scope catalog gives you what is actually running in an environment. draft-apis:get gives you the development copy in the pOrg. After a few manual UI edits by colleagues, these can differ — diffing the two is a genuinely useful audit trick.

Part B: the same thing with curl

The toolkit is a wrapper over the Platform REST API. Two steps make that concrete.

Step 1: watch the toolkit make REST calls

apic products:list-all --server $MGMT --org $ORG \
     --scope catalog --catalog sandbox --debug

The debug output shows the exact request, e.g. GET https://$MGMT/api/catalogs/$ORG/sandbox/products. This is your universal endpoint-discovery tool: any workflow you can do in the CLI, --debug hands you the REST recipe for.

Step 2: do it yourself

The Platform API uses OAuth password-grant tokens. You need a client_id/client_secret pair identifying your tool: the credentials file that ships with the toolkit download works (the CMC/API Manager "Download toolkit" tile offers client-creds), or an admin can mint a dedicated one with apic registrations:create — see IBM's REST API First Steps.

# 1. Get a Bearer token (valid ~8h)
curl -sk -X POST https://$MGMT/api/token \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{
    "username":      "you@company.example",
    "password":      "********",
    "realm":         "provider/default-idp-2",
    "client_id":     "'$CLIENT_ID'",
    "client_secret": "'$CLIENT_SECRET'",
    "grant_type":    "password"
  }'
# → { "access_token": "eyJhbGci…", "token_type": "Bearer", "expires_in": 28800 }

# 2. Use it — list products in the catalog, straight from the API
curl -sk "https://$MGMT/api/catalogs/$ORG/sandbox/products" \
  -H "Authorization: Bearer $TOKEN" -H "Accept: application/json"

Bonus discovery endpoint — the realm list needs no authentication at all (handy for scripts that must work on a fresh machine):

curl -sk https://$MGMT/api/cloud/provider/identity-providers

Why this matters for your mission

This token flow is exactly what a CI/CD job does: no toolkit binary required, just curl against /api/token and the Provider API. The full endpoint reference is the v10 API Explorer. Lesson 5 turns this into a real pipeline.
