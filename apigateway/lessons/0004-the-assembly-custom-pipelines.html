The Assembly — Your Custom Pipeline

The "custom pipeline" you asked about on day one is the assembly: an ordered list of policies plus one shared context tree. Learn the tree, and every policy becomes obvious.

In Lesson 2 your assembly was a single invoke — a plain proxy. Real APIs need more: set headers, branch per operation, reshape a backend response, survive a backend outage. All of that happens in x-ibm-configuration.assembly, in YAML, in git — no UI required.

The mental model: one tree, many readers

Policies don't pipe values into each other. They all read and write a shared, JSON-like context tree (IBM Docs):

request.* the inbound request, frozen request.verb, request.parameters.zip message.* the payload flowing through ──► whatever is here at the end policies mutate this is the client's response api.* API metadata + properties api.operation.path, api.properties.target-url plan.* client.* who is calling, on which plan error.* filled inside catch blocks <yours> anything you invent e.g. an invoke's output: geo

Three access idioms, one tree: $(api.properties.target-url) in YAML fields, context.get('request.verb') / context.set(…) in GatewayScript, and condition expressions like request.verb==='GET' in a switch. (Older samples use apim.getvariable() — v5-era API, still works, but write context.*.)

The one rule of assemblies

message is the pipeline. An invoke without output: overwrites message with the backend response; whatever sits in message.body after the last policy is what the client receives. Every non-trivial assembly is just controlled mutation of message.

Worked example: enrich a response

FindBranch, upgraded: call the backend, keep its response out of the pipeline, then build a custom payload with a Google-Maps link. (Pattern from IBM's PoT Lab 5, modernized to the context.* API.)

assembly:
  execute:
    - invoke:                          # 1. call backend…
        version: 2.0.0
        title: get-branch
        target-url: $(target-url)/details?zip=$(request.parameters.zip)
        verb: GET
        output: branch                 # …but park response in 'branch',
                                       #    don't overwrite message
    - gatewayscript:                   # 2. build our own response payload
        version: 2.0.0
        title: build-response
        source: |
          var b = context.get('branch.body');
          context.message.body.write({
            id:        b.id,
            type:      b.type,
            maps_link: 'https://www.google.com/maps?q='
                       + b.address.lat + ',' + b.address.lng
          });
    - set-variable:                    # 3. polish headers
        version: 2.0.0
        title: response-headers
        actions:
          - set: message.headers.content-type
            value: application/json
          - clear: message.headers.x-backend-secret

  catch:                               # 4. backend down ≠ ugly 500
    - errors: [ ConnectionError ]
      execute:
        - set-variable:
            version: 2.0.0
            title: friendly-error
            actions:
              - set: message.status.code
                value: 503
              - set: message.body
                value: '{"error":"branch service unavailable, try later"}'

Four ideas in one assembly: output: keeps the pipeline clean, GatewayScript reads the tree and writes message.body, set-variable handles the mechanical bits cheaper than a script, and catch turns gateway errors into designed responses. Branching per operation is the same trick with switch/operation-switch — every policy's YAML shape is in the new assembly reference, including the rules of thumb for which policy to reach for.

Hands-on: read a real pipeline

The fastest way to learn assembly idioms is to read the ones already running at work:

# 1. Pull a colleague's deployed API (Lesson 3 skill)
apic apis:get some-api:1.0.0 --server $MGMT --org $ORG \
     --scope catalog --catalog sandbox

# 2. Read its x-ibm-configuration.assembly with fresh eyes:
#    - Where does message get overwritten? (invokes without output:)
#    - Any catch block, or do errors leak raw?
#    - Could any gatewayscript be a set-variable instead?

# 3. Edit locally, then lint — validate catches assembly errors too
apic validate the-file.yaml

Test without publishing

The API Designer (apic-designer, part of the toolkit download) has a local Explorer/Test mode, and testable: true APIs can be invoked in the Sandbox via the automatic test application. For quick iterations: publish to Sandbox, curl the gateway endpoint, watch message take shape — a log policy or console.error(context.get('…')) in GatewayScript shows up in DataPower logs (see Chris Phillips: Debugging an API).
